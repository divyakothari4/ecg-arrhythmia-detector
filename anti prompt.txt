Because the vast majority of heartbeats are "Normal", the model learned that it could achieve a 76% accuracy by basically guessing "Normal" most of the time. By passing class weights into our PyTorch CrossEntropyLoss, we heavily penalize the model whenever it misclassifies a rare beat (like an S or F).

However, we paid a heavy price in precision. Because the class weights for those rare classes are so high, the model became overly eager to predict them. It ended up misclassifying a lot of Normal beats as F or S, causing the overall accuracy to drop to 52%.

This is a classic machine learning tradeoff when dealing with extreme class imbalances (like 44k Normal beats vs. only 388 Fusion beats).

To fix this and get both high accuracy and high recall, we could try:

Focal Loss: Instead of just using static class weights, Focal Loss dynamically scales the loss based on confidence, which prevents the model from being overwhelmed by the massive number of easy-to-classify Normal beats.
SMOTE / Data Augmentation: Synthetically generating more examples of the rare classes so the dataset is actually balanced before it hits the model.
Model Complexity: Our 1D-CNN is quite small. We could add more layers, Residual blocks (ResNet), or an LSTM layer to capture better sequential patterns.

What went wrong?
The model literally did not predict a single Normal (N) beat correctly out of 44,653 attempts! It predicted everything as one of the rare classes.

Why? Because our class weights were too extreme. There are 44,653 Normal beats and only 388 Fusion (F) beats. Scikit-learn assigned a massive weight to F and a microscopic weight to N. Combined with Focal Loss (which already down-weights easy examples), the penalty for guessing N incorrectly dropped to almost exactly zero. The model realized that mathematically, the safest bet is to just never guess N.

This is a very common trap in imbalanced time-series data!

How we can fix this:
Smooth the Weights: Instead of using raw inverse frequencies, we take the square root or log of the class weights so they aren't so drastically different.
Drop alpha from Focal Loss: Focal Loss actually handles imbalance naturally using its gamma parameter. Passing in raw class weights on top of it was overkill. We can just remove the alpha weights.
Try SMOTE: Instead of messing with the loss function, we just synthetically generate more rare beats (using SMOTE) until the dataset is perfectly balanced, and go back to a standard CrossEntropyLoss.
